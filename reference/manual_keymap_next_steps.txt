ROS2 컨트롤러 입력 구조 설명
============================

이 문서는 실행 방법이 아니라, 현재 프로젝트에서 컨트롤러 입력이 ROS2 안에서 어떤 구조로 흘러가는지 설명하기 위한 문서다.


1. ROS2에서 제일 중요한 개념
---------------------------

ROS2 시스템은 여러 개의 작은 프로그램이 서로 메시지를 주고받는 구조다.

이 작은 프로그램 하나하나를 노드(node)라고 부른다.

예를 들어 나중에 이 차량 시스템은 대략 이런 노드들로 나뉠 수 있다.

  - joy_node
  - manual_control_node
  - vesc_interface_node
  - camera_node
  - lane_detection_node

각 노드는 한 가지 역할만 맡는 것이 좋다.

예:

  joy_node는 컨트롤러 입력만 읽는다.
  manual_control_node는 컨트롤러 입력을 차량 명령으로 바꾼다.
  vesc_interface_node는 차량 명령을 VESC 시리얼 패킷으로 바꿔 전송한다.

이렇게 나누면 한 부분을 고쳐도 전체를 다시 만들 필요가 줄어든다.


2. 토픽(topic)이란 무엇인가
---------------------------

토픽은 노드들이 메시지를 주고받는 통로 이름이다.

예를 들어 /joy라는 토픽이 있다.

  joy_node
    -> /joy
    -> manual_control_node

이 말은 joy_node가 /joy라는 이름의 통로에 메시지를 보내고, manual_control_node가 /joy를 구독해서 메시지를 받는다는 뜻이다.

ROS2에서는 메시지를 보내는 쪽을 publish한다고 말한다.
메시지를 받는 쪽을 subscribe한다고 말한다.

정리하면:

  publish   = 토픽에 메시지를 발행한다
  subscribe = 토픽에서 메시지를 구독한다
  topic     = 메시지가 오가는 이름 있는 통로


3. 메시지 타입(message type)이란 무엇인가
-----------------------------------------

토픽에는 아무 데이터나 보내는 것이 아니라 정해진 형식의 메시지를 보낸다.

/joy 토픽의 메시지 타입은 다음이다.

  sensor_msgs/msg/Joy

이 타입은 컨트롤러 입력을 담기 위한 표준 ROS2 메시지다.

대략 이런 구조를 가진다.

  axes:    실수 배열
  buttons: 정수 배열

예:

  axes[0]    -> 왼쪽 스틱 좌우
  axes[1]    -> 왼쪽 스틱 상하
  buttons[0] -> A 버튼

중요한 점은 /joy 메시지는 "A 버튼" 같은 이름을 직접 담지 않는다는 것이다.
그냥 배열 번호와 값만 들어 있다.

그래서 "buttons[0]이 A 버튼이다" 같은 의미 해석은 따로 관리해야 한다.
그 역할을 manual_keymap.yaml이 맡는다.


4. joy_node의 역할
------------------

joy_node는 ROS2 joy 패키지에 들어있는 기본 노드다.

joy_node가 하는 일은 간단하다.

  1. 리눅스 조이스틱 장치(/dev/input/js1)를 읽는다.
  2. 입력 상태를 sensor_msgs/msg/Joy 메시지로 만든다.
  3. /joy 토픽으로 발행한다.

joy_node는 컨트롤러 입력을 "차량 명령"으로 바꾸지 않는다.

즉 joy_node는 이런 것을 모른다.

  - 이 버튼이 A인지 B인지
  - 이 스틱을 조향으로 쓸지 속도로 쓸지
  - duty 값이 얼마인지
  - servo 값이 얼마인지
  - VESC로 어떤 패킷을 보내야 하는지

joy_node는 단지 raw 입력을 ROS2 메시지로 바꾸는 역할만 한다.


5. /joy 토픽의 의미
-------------------

/joy는 컨트롤러의 현재 상태를 담은 토픽이다.

컨트롤러를 움직이면 joy_node가 계속 /joy 메시지를 발행한다.

예를 들어 왼쪽 스틱을 오른쪽으로 밀면:

  axes[0] 값이 0.0에서 1.0 쪽으로 변한다.

A 버튼을 누르면:

  buttons[0] 값이 0에서 1로 변한다.

A 버튼을 떼면:

  buttons[0] 값이 1에서 0으로 돌아온다.

즉 /joy는 "차량을 움직여라"가 아니라 "컨트롤러가 지금 이런 상태다"를 나타낸다.


6. manual_keymap.yaml의 역할
----------------------------

manual_keymap.yaml은 /joy 배열의 번호에 의미를 붙여주는 설정 파일이다.

현재 컨트롤러에서는 예를 들어 다음과 같다.

  left_stick.x  -> axes[0]
  left_stick.y  -> axes[1]
  right_stick.x -> axes[2]
  right_stick.y -> axes[3]

  A -> buttons[0]
  B -> buttons[1]
  X -> buttons[3]
  Y -> buttons[4]

  RT -> axes[4], buttons[9]
  LT -> axes[5], buttons[8]

이 파일이 필요한 이유는 컨트롤러마다 버튼 번호가 다를 수 있기 때문이다.

예를 들어 어떤 컨트롤러에서는 A 버튼이 buttons[0]일 수 있고, 다른 컨트롤러에서는 buttons[1]일 수도 있다.

코드 안에 버튼 번호를 직접 박아두면 컨트롤러가 바뀔 때 코드를 수정해야 한다.
반대로 manual_keymap.yaml에 번호를 적어두면 설정 파일만 바꾸면 된다.


7. manual_keymap.yaml은 노드가 아니다
-------------------------------------

manual_keymap.yaml은 프로그램이 아니다.
토픽을 발행하지도 않고, 컨트롤러를 읽지도 않는다.

그냥 설정 파일이다.

나중에 manual_control_node가 시작할 때 이 파일을 읽는다.
그리고 /joy 메시지를 해석할 때 참고한다.

예:

  manual_keymap.yaml에 "A button은 number 0"이라고 적혀 있다.
  manual_control_node가 /joy 메시지를 받는다.
  manual_control_node는 joy_msg.buttons[0]을 보고 A 버튼 상태를 판단한다.


8. manual_control_node의 역할
-----------------------------

manual_control_node는 아직 구현하지 않았지만, 다음 단계에서 만들 가능성이 높은 노드다.

역할은 /joy 입력을 차량이 이해할 수 있는 수동 주행 명령으로 바꾸는 것이다.

예상 입력:

  /joy

예상 출력:

  /manual_drive_command
  또는 /drive_command

manual_control_node는 이런 일을 한다.

  1. /joy 토픽을 구독한다.
  2. manual_keymap.yaml을 읽는다.
  3. vehicle_limits_manual.yaml을 읽는다.
  4. 스틱 값과 버튼 값을 해석한다.
  5. 조향 명령과 속도 명령을 계산한다.
  6. 계산된 명령을 다른 토픽으로 발행한다.

중요한 점은 manual_control_node도 VESC에 직접 시리얼 패킷을 보내지 않는 편이 좋다는 것이다.
수동 입력 해석과 VESC 통신은 서로 다른 책임이기 때문이다.


9. vehicle_limits_manual.yaml의 역할
------------------------------------

manual_keymap.yaml이 "어떤 버튼이 몇 번인가"를 설명한다면, vehicle_limits_manual.yaml은 "수동제어에서 차량을 어느 범위까지 움직일 수 있는가"를 설명한다.

예:

  - 최대 duty
  - 최소 duty
  - 조향 servo 최소값
  - 조향 servo 최대값
  - deadzone
  - 급격한 변화 제한
  - deadman 버튼 필요 여부

manual_keymap.yaml은 컨트롤러 자체에 대한 정보다.
vehicle_limits_manual.yaml은 차량 안전 한계에 대한 정보다.

이 둘은 역할이 다르다.

예:

  manual_keymap.yaml:
    RT는 axes[4]다.

  vehicle_limits_manual.yaml:
    RT를 끝까지 눌러도 duty는 0.08을 넘지 않는다.


10. VESC 노드의 역할
--------------------

VESC는 실제 모터 컨트롤러다.

나중에 vesc_interface_node가 맡을 역할은 차량 명령을 VESC가 이해하는 시리얼 패킷으로 바꿔 보내는 것이다.

예상 구조:

  /drive_command
    -> vesc_interface_node
    -> /dev/ttyACM0
    -> VESC

vesc_interface_node는 컨트롤러 버튼 번호를 알 필요가 없다.
반대로 manual_control_node는 VESC packet byte를 알 필요가 없다.

이렇게 역할을 나누는 것이 ROS2 스타일에 맞다.


11. 전체 수동제어 구조
----------------------

최종적으로 수동제어는 대략 이런 구조가 된다.

  8BitDo Controller
    -> joy_node
    -> /joy
    -> manual_control_node
    -> /drive_command
    -> vesc_interface_node
    -> VESC
    -> motor / servo

각 단계의 의미:

  8BitDo Controller:
    사람이 누르는 물리 입력 장치

  joy_node:
    컨트롤러 raw 입력을 /joy로 발행

  /joy:
    컨트롤러 상태 메시지

  manual_control_node:
    /joy를 해석해서 차량 명령 생성

  /drive_command:
    차량이 원하는 속도/조향 명령

  vesc_interface_node:
    차량 명령을 VESC 시리얼 packet으로 변환

  VESC:
    실제 모터와 서보를 제어


12. 왜 이렇게 여러 단계로 나누는가
----------------------------------

한 파일에서 컨트롤러도 읽고, 조향도 계산하고, VESC도 제어할 수는 있다.
초기 테스트에서는 그렇게 해도 된다.

하지만 시스템이 커지면 문제가 생긴다.

예를 들어:

  - 컨트롤러만 바꾸고 싶은데 VESC 코드까지 건드리게 된다.
  - 자동주행을 붙이려는데 수동주행 코드와 섞인다.
  - 안전 제한을 바꾸려는데 통신 코드까지 이해해야 한다.
  - 테스트할 때 실제 차량을 움직이지 않고 입력만 확인하기 어렵다.

ROS2에서는 이런 문제를 줄이기 위해 역할을 나눠서 노드를 만든다.

좋은 분리 예:

  joy_node:
    입력 장치 담당

  manual_control_node:
    수동 주행 판단 담당

  autonomous_control_node:
    자동 주행 판단 담당

  safety_limiter_node:
    명령 제한 담당

  vesc_interface_node:
    하드웨어 통신 담당


13. raw 입력과 차량 명령은 다르다
---------------------------------

/joy는 raw 입력이다.

예:

  axes[0] = 0.7
  buttons[0] = 1

이 값만으로는 차량이 어떻게 움직여야 하는지 아직 정해지지 않았다.

manual_control_node가 정책을 정해야 한다.

예:

  axes[0]을 조향으로 쓸 것인가?
  axes[1]을 속도로 쓸 것인가?
  RT를 전진으로 쓸 것인가?
  LT를 후진으로 쓸 것인가?
  LB를 deadman 버튼으로 쓸 것인가?
  A 버튼을 정지 버튼으로 쓸 것인가?

이 정책을 정한 뒤에야 차량 명령이 된다.


14. normalized 값이 필요한 이유
-------------------------------

리눅스 조이스틱 장치는 axis 값을 보통 -32767에서 32767 사이의 정수로 준다.

하지만 제어 계산에서는 -32767 같은 큰 정수보다 -1.0에서 1.0 사이의 값이 다루기 쉽다.

예:

  raw -32767 -> normalized -1.0
  raw      0 -> normalized  0.0
  raw  32767 -> normalized  1.0

그래서 manual_keymap.yaml에는 raw 값과 normalized 기준을 같이 적어둔다.

나중에 manual_control_node는 normalized 값을 기준으로 계산하면 된다.


15. 스틱 입력을 조향으로 쓸 때 주의할 점
----------------------------------------

스틱은 사람이 완벽하게 수평으로 밀기 어렵다.
왼쪽이나 오른쪽으로 민다고 해도 약간 위아래 성분이 섞일 수 있다.

그래서 조향을 계산할 때는 스틱 전체 방향을 보지 말고, 조향에 사용할 축 하나만 보는 것이 좋다.

예:

  left_stick.x만 조향으로 사용
  left_stick.y는 조향 계산에 사용하지 않음

이렇게 하면 대각선 성분이 조향각을 직접 바꾸지 않는다.

다만 대각선으로 밀면 x축 값이 완전한 1.0까지 안 갈 수 있으므로, 최대 조향이 살짝 덜 나올 수 있다.
이것은 나중에 gain이나 deadzone으로 조절할 수 있다.


16. LT/RT가 axis와 button을 둘 다 가지는 이유
---------------------------------------------

LT/RT는 아날로그 트리거다.

그래서 두 종류의 정보가 나온다.

첫 번째는 axis 정보다.

  얼마나 눌렀는지

두 번째는 button 정보다.

  눌렸는지, 안 눌렸는지

예:

  RT axis:
    안 누름 -> -1.0 근처
    중간    ->  0.0 근처
    끝까지  ->  1.0 근처

  RT button:
    안 누름 -> 0
    눌림    -> 1

속도 제어처럼 세기가 필요한 입력은 axis를 쓰는 것이 좋다.
단순 ON/OFF 용도는 button을 쓰는 것이 좋다.


17. 지금 단계에서 확인하려는 것
-------------------------------

현재 단계에서 확인하려는 것은 단 하나다.

  컨트롤러를 움직이면 /joy 토픽의 axes/buttons 값이 변하는가?

이것이 확인되면 입력 계층은 준비된 것이다.

차량이 움직이지 않아도 정상이다.
아직 /joy를 차량 명령으로 바꾸는 노드를 만들지 않았기 때문이다.


18. 이후 개발 순서
------------------

추천 순서는 다음과 같다.

  1. joy_node로 /joy 발행 확인
  2. manual_keymap.yaml 확정
  3. vehicle_limits_manual.yaml 확정
  4. manual_control_node 작성
  5. /joy를 /manual_drive_command로 변환
  6. 안전 제한 적용
  7. vesc_interface_node 작성
  8. /drive_command를 VESC packet으로 변환
  9. 낮은 duty와 제한된 servo 범위에서 실제 차량 테스트

각 단계는 독립적으로 확인하는 것이 좋다.

예:

  /joy가 잘 나오는지 확인
  /manual_drive_command가 잘 나오는지 확인
  VESC에 정지 명령이 잘 가는지 확인
  낮은 속도 명령만 먼저 보내기


19. 핵심 요약
-------------

현재 프로젝트에서 각 파일/노드의 역할은 다음과 같다.

  controller_input_test.py:
    컨트롤러 키 번호 조사용 도구

  manual_keymap.yaml:
    /joy 배열 번호에 이름을 붙여주는 설정 파일

  joy_test.launch.py:
    joy_node만 실행해서 /joy 발행을 확인하는 launch 파일

  joy_node:
    컨트롤러 raw 입력을 sensor_msgs/msg/Joy로 발행하는 ROS2 기본 노드

  manual_control_node:
    아직 미구현. 나중에 /joy를 차량 명령으로 변환할 노드

  vesc_interface_node:
    아직 미구현. 나중에 차량 명령을 VESC 시리얼 패킷으로 변환할 노드

가장 중요한 구분:

  /joy는 컨트롤러 상태다.
  /drive_command는 차량 명령이다.
  VESC packet은 하드웨어 통신 데이터다.

이 세 가지를 섞지 않는 것이 구조를 깔끔하게 유지하는 핵심이다.
